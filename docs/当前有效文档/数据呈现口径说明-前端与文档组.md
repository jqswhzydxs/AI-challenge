# 数据呈现口径说明（前端组与文档组）

## 1. 当前推荐总口径

本项目当前不建议表述为“完整协同优化求解系统”，更稳妥的表述是：

> 基于后端模拟采集装置或外部采集程序持续写入的能源时序数据，以及用户录入的次日订单产量，后端调用算法生成生产计划和 MPC 调控结果，并对生产计划与能源运行方案进行协同评估、约束校验和效果分析。

系统重点展示的是：

- 生产计划结果展示
- 分钟级能源数据采集与展示
- 能源运行方案测算
- 生产计划与能源运行方案的协同评估
- 约束校验与效果分析

不建议使用以下表述：

- 协同优化模型已完成
- 能源优化模型输出
- 协同方案生成
- 最优协同方案
- 真实现场实时生产数据

## 1.1 v1.2 前端主流程口径

当前正式前端流程为：

```text
后端模拟采集装置每分钟写入 energy_realtime_data
        ↓
前端能源页面按分钟查询 /api/energy/realtime
        ↓
调度人员录入计划日期和订单产量
        ↓
前端调用 /api/production/schedules/generate-from-collected-data
        ↓
后端读取最近 7 天能源数据并调用算法
        ↓
算法生成排产方案和 MPC 初始指令
        ↓
RealtimeMpcControlTask 每分钟根据最新工况滚动修正 MPC
        ↓
前端轮询 taskId 并展示排产、MPC 最新指令和协同评估结果
```

前端正式页面不再提供“上传能源 CSV 并生成方案”作为主操作。旧接口 `generate-from-raw-data` 仅保留为历史数据补录、算法联调和兜底测试入口。

## 3. 排产是否已经考虑能源因素

根据当前数据库中保留的算法组排产结果，可以判断：**算法组排产结果已经体现了能耗优化因素，但不能证明它已经完整纳入能源运行系统约束。**

数据库证据：

```text
production_schedule_plan.id = 4000000000000000101
objective = MIN_EC
raw_plan_json 中包含：
EC_baseline = 14
EC_optimized = 13.278524
EC_reduction = 5.1534
total_energy = 125.969628
optimal_temperature = 1140
optimal_speed = 11
```

可以说明：

> 算法组排产结果中已经包含能耗指标，目标体现为降低单位能耗或能耗水平。

不建议进一步说明：

> 算法组已经完整实现生产计划与能源系统的联合优化。

原因是当前数据里没有看到以下能源运行约束的明确证据：

- 峰谷电价约束
- 蒸汽供应约束
- 碳排放约束
- 能源设备容量约束
- 负荷削峰填谷约束
- 储能、锅炉、能源介质调度约束

推荐口径：

> 从现有排产结果看，算法组已将能耗指标纳入排产优化，排产目标为 `MIN_EC`，并给出了优化前后单位能耗、总能耗等指标。但当前数据无法证明其已完整纳入峰谷电价、蒸汽供应、碳排放、能源设备能力等能源运行约束。因此系统后端继续基于排产结果生成能源运行方案，并通过协同评估模块补充能源侧约束校验和效果分析。

## 4. 各模块命名建议

### 4.1 排产模块

推荐名称：

- 生产计划
- 排产方案
- 算法组排产结果

可说明：

> 排产方案来自算法组提供的 `daily_plan_v3.2.json` 文件，后端完成导入、存储和展示。该排产结果已体现单位能耗优化指标。

不建议说：

- 后端生成真实排产最优解
- 后端内置排产优化模型
- 当前系统已完成生产与能源联合求解

### 4.2 能源模块

推荐名称：

- 能源运行方案
- 能源运行测算方案
- 基于生产计划的能源运行方案

可说明：

> 能源运行方案由后端基于排产结果、分时电价和能源换算系数生成，用于展示能源消耗、成本、蒸汽消耗和碳排估算。

不建议说：

- 算法组能源优化模型输出
- 能源最优调度方案
- 真实能源优化求解结果

### 4.3 协同评估模块

推荐名称：

- 协同评估
- 协同评估结果
- 约束校验
- 效果分析

推荐完整表述：

> 生产计划与能源运行方案的协同评估、约束校验和效果分析。

不建议继续使用：

- 协同优化方案
- 协同方案生成
- 协同最优方案

协同模块的定位：

```text
排产方案回答“生产怎么排”
能源方案回答“能源怎么跟上”
协同评估回答“两者匹配得好不好”
```

也就是说，协同模块不是再生成第三套方案，而是进行复核和分析，包括：

- 排产电耗和能源电耗是否一致
- 高负荷时段是否撞上峰电价
- 能源成本是否合理
- 蒸汽、碳排是否超约束
- 是否存在约束冲突
- 整体效果指标是否可接受

## 5. 能源运行方案生成逻辑

当前能源运行方案不是外部能源优化模型输出，而是后端规则测算结果。

生成逻辑：

1. 查询指定日期是否有能源时序数据。
2. 如果有可用能源时序数据，则按小时聚合电耗、蒸汽、碳排。
3. 如果没有对应日期能源时序数据，则基于当天排产方案明细派生能源运行方案。
4. 当前 `2026-07-17` 保留方案主要基于算法组排产结果派生。

主要计算假设：

```text
electricity = 排产明细中的 elecForecast
output = production * 100
steam = electricity * 0.005
carbon = electricity * 0.00057
energyCost = electricity * 分时电价 + steam * 蒸汽单价
```

这些系数和参数的来源说明：

| 参数/公式 | 当前来源 | 推荐表述 |
| --- | --- | --- |
| `elecForecast` | 算法组排产结果中的电耗预测字段 | 来自算法组排产结果 |
| `production` | 算法组排产结果中的产量字段 | 来自算法组排产结果 |
| `output = production * 100` | 后端展示尺度换算 | 系统展示换算，不作为真实生产公式 |
| `steam = electricity * 0.005` | 后端规则测算系数 | 蒸汽消耗估算系数 |
| `carbon = electricity * 0.00057` | 后端规则测算系数 | 碳排放估算系数 |
| 分时电价 | 后端当前内置峰平谷价格 | 当前测算假设，后续可配置化 |
| 蒸汽单价 `180.00` | 接口参数或默认值 | 当前成本测算参数 |

分时电价：

| 时段 | 类型 | 电价 |
| --- | --- | --- |
| 00:00-08:00 | 谷段 | 0.35 |
| 08:00-18:00 | 平段 | 0.65 |
| 18:00-22:00 | 峰段 | 1.05 |
| 22:00-24:00 | 平段 | 0.65 |

推荐说明：

> `elecForecast` 和 `production` 来自算法组排产结果；蒸汽、碳排、电价和蒸汽单价目前是系统测算假设，用于完成能源运行方案展示和协同评估，不作为真实生产模型参数。后续可由算法组或业务方确认正式参数后配置化替换。

## 9. 答辩追问建议

如果被问：“排产有没有考虑能源因素？”

建议回答：

> 从当前排产结果看，算法组已经把能耗指标纳入排产结果，目标为 `MIN_EC`，并提供了 `EC_baseline`、`EC_optimized`、`EC_reduction`、`total_energy` 等指标。但现有数据不能证明排产模型已经完整纳入峰谷电价、蒸汽供应、碳排放、能源设备能力等能源运行约束。因此系统通过能源运行测算和协同评估模块补充能源侧分析。

如果被问：“能源方案是不是算法组给的？”

建议回答：

> 排产方案是算法组给出的结果文件。能源侧当前使用算法组清洗后的历史能耗数据，并结合排产结果、分时电价和能源换算系数生成能源运行方案。它主要用于协同评估和效果分析，不表述为独立能源优化模型输出。

如果被问：“有没有协同优化模型？”

建议回答：

> 当前后端实现的是生产计划与能源运行方案的协同评估、约束校验和效果分析，尚未接入独立协同优化求解模型。后续如果算法岗提供目标函数、约束条件、输入输出格式和模型接口，后端可以将现有规则测算逻辑替换为模型调用。

如果被问：“这些数据真实吗？”

建议回答：

> 基础数据来自算法组基于历史数据清洗后的样本数据，排产结果来自算法组文件导入。能源运行方案和协同评估结果是在这些数据基础上的规则测算和评估结果，主要用于展示生产与能源协同分析链路。
