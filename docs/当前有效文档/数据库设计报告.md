# 数据库设计报告

> 项目名称：生产-能源交互式优化平台  
> 版本：v1.0 正式整理稿  
> 整理日期：2026-08-01  
> 数据库：MySQL 8.0

## 1. 设计目标

数据库用于支撑生产计划、能源运行方案、MPC 实时调控、协同评估、报表展示和系统管理。设计目标包括：

- 保存用户上传原始数据触发的算法任务、算法输出结果、排产结果和 MPC 调控结果。
- 保留算法组提供的历史能耗数据、排产结果和 MPC 调控结果，作为联调和演示兜底数据。
- 支撑后端根据算法排产结果生成能源运行测算方案。
- 支撑生产计划与能源运行方案的协同评估、约束校验和效果分析。
- 支撑前端登录、权限、首页看板、历史列表、告警和报表展示。
- 保留算法输入文件、输出 JSON/CSV 转换信息，方便复现和答辩说明数据来源。

## 2. 数据来源分层

| 数据层 | 说明 | 典型表 |
| --- | --- | --- |
| 算法数据层 | 用户上传 CSV 后由后端调用算法生成结果；算法组提供的 CSV/JSON/MAT 结果保留为兜底导入 | `algorithm_task`、`steel_energy_dataset`、`energy_realtime_data`、`production_schedule_plan`、`production_schedule_detail`、`mpc_realtime_control` |
| 后端派生层 | 后端基于算法数据、能源价格和约束规则生成 | `energy_plan`、`energy_plan_detail`、`joint_optimization_plan`、`joint_optimization_timeseries`、`constraint_conflict` |
| 联调展示层 | 为系统运行、页面展示和联调补齐的数据 | `sys_user`、`sys_role`、`production_order`、`energy_equipment`、`warning_record`、`report_statistic` |
| 指标分析层 | 保存 MAPE、EC、ER、降本、碳减排等评价指标 | `evaluation_metric` |

## 3. 主要业务链路

```text
算法组历史能源数据
        -> energy_realtime_data / steel_energy_dataset

用户上传原始能源 CSV
        -> algorithm_task
        -> 后端调用 Python generate_plan.py
        -> output.json
        -> production_schedule_plan
        -> production_schedule_detail
        -> evaluation_metric
        -> mpc_realtime_control

算法组日级排产结果 daily_plan_v3.2.json（兜底导入）
        -> algorithm_task
        -> production_schedule_plan
        -> production_schedule_detail
        -> evaluation_metric

后端能源运行测算
        -> energy_plan
        -> energy_plan_detail

后端协同评估
        -> joint_optimization_plan
        -> joint_optimization_timeseries
        -> constraint_conflict

算法组 MPC 结果
        -> mpc_realtime_control
```

## 4. 核心表设计

### 4.1 系统权限表

| 表名 | 用途 |
| --- | --- |
| `sys_user` | 系统用户，支持登录、用户管理和操作人记录。 |
| `sys_role` | 角色配置，例如系统管理员、生产调度员、能源管理员。 |
| `sys_user_role` | 用户角色关联表。 |
| `sys_operation_log` | 操作日志，用于系统管理页面和审计展示。 |

当前联调默认账号：

| 账号 | 角色 | 用途 |
| --- | --- | --- |
| `admin` | 系统管理员 | 全局管理和演示 |
| `dispatcher` | 调度员 | 生产排产模块演示 |
| `energy` | 能源管理员 | 能源运行模块演示 |

### 4.2 生产侧表

| 表名 | 用途 | 数据来源 |
| --- | --- | --- |
| `production_line` | 产线基础数据 | 联调模拟 |
| `production_equipment` | 生产设备基础数据 | 联调模拟 |
| `production_order` | 生产订单数据 | 联调模拟 |
| `production_schedule_plan` | 排产方案主表 | 算法组 `daily_plan_v3.2.json` 转换入库，部分历史为联调模拟 |
| `production_schedule_detail` | 排产小时明细 | 算法组排产 JSON 拆表，部分字段后端补齐 |

`production_schedule_plan` 关键字段：

| 字段 | 含义 |
| --- | --- |
| `task_id` | 对应 `algorithm_task` |
| `schedule_date` | 排产日期 |
| `plan_start_time` | 计划开始时间 |
| `plan_horizon` | 计划跨度，当前为 24 |
| `objective` | 优化目标，主案例为 `MIN_EC` |
| `ec_baseline` | 优化前 EC，当前主口径为 `14.00` |
| `ec_optimized` | 优化后 EC，当前主口径为 `13.2785` |
| `ec_reduction` | EC 降低率，当前主口径为 `5.15%` |
| `total_production` | 总排产量 |
| `total_energy` | 总预测能耗 |
| `raw_plan_json` | 算法排产结果原文 |

`production_schedule_detail` 中 `demand`、`production` 来自算法排产结果；`elec_forecast` 在新版 JSON 未提供时由后端按 `production × EC_optimized` 推导；`line_id`、`equipment_id`、`order_id`、`equipment_load_rate` 为联调展示补齐。

### 4.3 能源侧表

| 表名 | 用途 | 数据来源 |
| --- | --- | --- |
| `energy_medium` | 能源介质配置，如电力、蒸汽 | 联调模拟 |
| `energy_equipment` | 能源设备配置，如锅炉、汽轮机 | 联调模拟，约束按算法报告 |
| `energy_realtime_data` | 能源时序数据 | 算法组能源数据转换，另有演示兜底数据 |
| `steel_energy_dataset` | 钢铁能源样本数据 | 算法组 `steel_data_cleaned.csv` 转换 |
| `energy_production_history` | 生产-能源历史融合预留表 | 当前预留 |

当前能源设备约束：

| 设备 | 最小输出 | 最大输出 |
| --- | --- | --- |
| 锅炉 | `20 MW` | `80 MW` |
| 汽轮机 | `5 MW` | `30 MW` |

`energy_realtime_data` 采用 `(timestamp, source)` 唯一键，允许同一时间戳下保存不同来源的数据，例如 15 分钟样本、1 分钟样本和联调兜底数据。

### 4.4 能源运行方案表

| 表名 | 用途 |
| --- | --- |
| `energy_plan` | 能源运行方案主表 |
| `energy_plan_detail` | 能源运行方案时序明细 |

能源方案当前不是算法组独立 `energy_plan.json` 输出，而是后端基于以下数据派生：

- 指定日期的 `energy_realtime_data`。
- 如果当天无能源时序数据，则使用 `production_schedule_plan/detail`。
- 分时电价策略。
- 蒸汽、碳排和成本估算系数。

当前峰谷电价时间口径：

| 时段 | 时间 |
| --- | --- |
| 谷段 | `00:00-08:00,22:00-24:00` |
| 峰段 | `08:00-22:00` |
| 平段 | 算法报告未设单独平段，系统保留兼容字段 |

### 4.5 协同评估表

| 表名 | 用途 |
| --- | --- |
| `joint_optimization_plan` | 协同评估主表 |
| `joint_optimization_timeseries` | 协同评估时序明细 |
| `constraint_conflict` | 约束冲突记录 |
| `evaluation_metric` | 评价指标记录 |

当前模块更准确的业务定位是“协同评估、约束校验和效果分析”，不是独立协同优化求解模型。

主指标口径：

| 指标 | 当前值 | 含义 |
| --- | --- | --- |
| MAPE | `3.55%` | 平均绝对百分误差 |
| 仿真精度 | `96.45%` | `100 - MAPE` |
| EC | `5.15%` | 轧钢能耗降低率 |
| ER | `100%` | 方案可执行率 |

### 4.6 MPC 实时调控表

| 表名 | 用途 |
| --- | --- |
| `mpc_realtime_control` | 保存 MPC 实时调控指令 |

核心字段：

| 字段 | 含义 |
| --- | --- |
| `boiler_load_mw` | 锅炉负荷指令，范围 `20-80 MW` |
| `turbine_output_mw` | 汽机出力指令，范围 `5-30 MW` |
| `grid_purchase_kwh` | 外购电力 |
| `power_factor_target` | 功率因数目标，当前为 `0.95` |
| `elec_next_5min_kwh` | 未来 5 分钟电耗预测 |
| `steam_next_5min_t` | 未来 5 分钟蒸汽预测 |
| `source_file_name` | 来源文件 |
| `raw_json` | 原始记录 |

核心调控数值来自算法组 `mpc_results_final.csv` 和 `mpc_results_hourly.csv`，后端负责转换、校验和字段补齐。

## 5. 表关系概览

```text
sys_user -> sys_user_role -> sys_role
sys_user -> sys_operation_log

algorithm_task -> production_schedule_plan -> production_schedule_detail
algorithm_task -> energy_plan -> energy_plan_detail
algorithm_task -> joint_optimization_plan
algorithm_task -> mpc_realtime_control

production_schedule_plan -> joint_optimization_plan
energy_plan -> joint_optimization_plan
joint_optimization_plan -> joint_optimization_timeseries

energy_realtime_data -> energy_plan_detail
evaluation_metric -> production_schedule_plan / energy_plan / joint_optimization_plan
```

## 6. 索引与约束设计

- 主键统一使用 `BIGINT`。
- 业务状态字段统一使用 `VARCHAR(32)`。
- 大型 JSON 使用 `LONGTEXT` 或 `JSON` 兼容字段。
- 能源实时数据使用 `(timestamp, source)` 唯一键，避免 15 分钟数据和 1 分钟数据时间戳冲突。
- MPC 调控使用 `(control_date, control_time)` 唯一键，确保同一天同一分钟只保留一条调控记录。
- 主要历史查询字段建立索引，如 `schedule_date`、`plan_date`、`create_time`、`task_type/status`。

## 7. 当前完成度与后续优化

当前数据库设计已支撑后端接口和联调演示，主要表结构已落地。后续可继续优化：

- 将峰谷电价、蒸汽单价、碳排系数等从代码常量迁移到 `system_config`。
- 如果算法组提供独立能源优化模型，新增或扩展能源模型结果表。
- 如果算法组提供设备级排产和负荷曲线，替换当前 `equipment_load_rate` 联调补齐逻辑。
- 报表统计后续由明细表定时聚合生成，减少手工 seed 数据比例。
- 大规模分钟级数据后续可考虑按月分表或迁移到时序数据库。
