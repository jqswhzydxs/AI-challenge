# 数据库表数据来源分析

> 目的：说明当前数据库各表中的数据来源，区分“算法组给的数据”“后端根据算法数据转换/派生的数据”“后端联调模拟数据”。  
> 结论日期：2026-07-25

## 1. 总体结论

当前数据库不是全部模拟数据，也不是全部算法组原始数据，而是三类数据混合：

| 类型 | 含义 | 典型表 |
|---|---|---|
| 算法组数据入库 | 算法组给 CSV/JSON，后端转成 SQL 入库，业务数值主要来自算法文件 | `steel_energy_dataset`、`energy_realtime_data`、`mpc_realtime_control`、部分 `production_schedule_plan/detail` |
| 后端派生数据 | 算法组没有直接给这类结果，后端根据排产、能源、MPC 或实时能源数据计算生成 | `energy_plan`、`energy_plan_detail`、`joint_optimization_plan`、`joint_optimization_timeseries`、`constraint_conflict` |
| 联调模拟数据 | 为了系统登录、菜单、首页、设备、订单、报表可展示而补的演示数据 | `sys_user`、`sys_role`、`production_order`、`energy_equipment`、`warning_record`、`report_statistic` |

一句话汇报口径：

> 能源历史数据、分钟级数据、MPC 调控结果和日级排产方案来自算法组；后端把这些文件转换成数据库结构，并基于它们派生能源方案和协同优化结果；用户、角色、设备、订单、告警、报表统计等属于联调演示支撑数据。

## 2. 按表逐项分析

| 表名 | 当前数据来源分类 | 说明 |
|---|---|---|
| `algorithm_task` | 混合：算法结果记录 + 后端派生任务记录 | `PRODUCTION_SCHEDULE`、`REALTIME_MPC` 任务来自算法文件导入记录；`ENERGY_PLAN`、`JOINT_OPTIMIZATION` 是后端调用接口生成时写入的任务记录。 |
| `constraint_conflict` | 后端派生 | 协同优化生成时，后端根据能源设备输出是否超过阈值等规则生成冲突记录。不是算法组直接给的原始文件。 |
| `energy_equipment` | 联调模拟数据 | 锅炉、汽轮机、外购电接口等设备基础数据，用于能源方案和页面展示。算法组数据没有提供真实设备台账。 |
| `energy_medium` | 联调模拟数据 | 电力、蒸汽等能源介质基础配置，用于页面展示和折算口径。 |
| `energy_plan` | 后端派生 | 算法组目前没有单独提供 `energy_plan.json`。该表由后端根据实时能源数据或排产方案生成能源运行方案主表。 |
| `energy_plan_detail` | 后端派生 | `energy_plan` 的明细。后端按小时聚合能源实时数据，或从排产明细推算电耗、蒸汽、碳排和成本。 |
| `energy_production_history` | 预留/暂未填充 | 建表和清空脚本中存在，设计上用于生产-能源历史数据，但当前 seed 文件没有导入数据，主流程暂未使用。 |
| `energy_realtime_data` | 算法组数据转换入库 | 主要来自 `steel_data_cleaned.csv` 和 `steel_data_1min_fixed.csv`。后端补了主键、标准时间、来源标识、数据质量等数据库字段。 |
| `evaluation_metric` | 混合：算法指标 + 后端/联调补充 | 排产评价指标来自 `daily_plan_v3.2.json` 口径；部分如 `mape`、`cost_saving`、`carbon_reduction` 在当前 seed 中用于演示和报表展示，属于后端补齐/联调指标。 |
| `joint_optimization_plan` | 后端派生 | 算法组没有直接给协同优化方案文件。后端根据排产方案和能源方案计算降本率、降耗率、执行率、MAPE 等。 |
| `joint_optimization_timeseries` | 后端派生 | 协同优化的时序明细，由后端把排产明细和能源方案明细按时间对齐生成。 |
| `mpc_realtime_control` | 算法组数据转换入库 | 来自 `mpc_results_final.csv`、`mpc_results_hourly.csv`。后端补了 `task_id`、`control_date`、`raw_json`、`source_file_name` 等字段；部分缺失字段有默认补值。 |
| `production_equipment` | 联调模拟数据 | 生产设备台账，例如加热炉、轧机、冷却段。算法组日级排产 JSON 没有提供真实设备台账。 |
| `production_line` | 联调模拟数据 | 生产线基础数据，例如热轧产线 1、热轧产线 2。用于页面和排产明细关联展示。 |
| `production_order` | 联调模拟数据 | 订单编号、产品、交期、状态等是后端为联调页面构造的演示订单。 |
| `production_schedule_detail` | 算法组数据转换 + 后端补齐 | 小时 `demand`、`production` 来自 `daily_plan_v3.2.json`；`elec_forecast` 由后端按 `production × EC_optimized` 计算；`line_id/equipment_id/order_id/equipment_load_rate` 是联调关联补齐。 |
| `production_schedule_plan` | 算法组数据转换入库 | 主体来自 `daily_plan_v3.2.json`，包括计划开始时间、计划跨度、总产量、总能耗、EC 指标等；后端补数据库主键、任务 ID、方案名称、状态等。 |
| `report_statistic` | 联调模拟统计数据 | 当前由 `seed_demo_data.sql` 直接插入日/月统计，用于首页和报表展示。不是算法组直接输出，也不是当前后端自动从全量明细稳定生成的真实统计表。 |
| `steel_energy_dataset` | 算法组数据转换入库 | 来自 `steel_data_cleaned.csv`，作为钢铁能源样本表保存。字段基本对应算法组能源数据集，后端补主键、标准时间、质量标识。 |
| `sys_operation_log` | 联调模拟数据 | 操作日志样例，用于系统页面展示。当前不是系统运行时真实审计日志沉淀出来的完整日志。 |
| `sys_role` | 联调模拟数据 | 系统管理员、普通用户两类角色，用于登录和权限测试。角色编码已和后端鉴权规则统一为 `ADMIN`、`USER`。 |
| `sys_user` | 联调模拟数据 | `admin`、`dispatcher`、`energy` 等默认联调账号。 |
| `sys_user_role` | 联调模拟数据 | 用户和角色的关联关系，用于登录后返回角色和接口鉴权。 |
| `system_config` | 预留/暂未填充 | 建表和清空脚本中存在，但当前 seed 文件没有插入配置数据。属于系统配置预留表。 |
| `warning_record` | 联调模拟数据 | 首页告警展示数据，例如能源负荷告警、订单风险告警。不是算法组直接给的告警结果。 |

## 3. 算法组直接给的数据对应哪些表

| 算法组文件 | 入库/影响表 | 当前口径 |
|---|---|---|
| `steel_data_cleaned.csv` | `energy_realtime_data`、`steel_energy_dataset` | 15 分钟粒度能源历史数据，共 35,040 行。 |
| `steel_data_1min_fixed.csv` | `energy_realtime_data` | 1 分钟能源数据；当前仓库是旧联调样本 132,481 行，最新正式口径是 PCHIP 重采样后的 3,155,026 行，后续需要重新生成 SQL。 |
| `daily_plan_v3.2.json` | `algorithm_task`、`production_schedule_plan`、`production_schedule_detail`、部分 `evaluation_metric` | 日级排产方案，后端拆成主表和 24 条小时明细。 |
| `mpc_results_final.csv` | `algorithm_task`、`mpc_realtime_control` | MPC 最终调控结果，120 条，当前入库日期 `2026-07-17`。 |
| `mpc_results_hourly.csv` | `algorithm_task`、`mpc_realtime_control` | MPC 小时聚合/分钟展开结果，120 条，当前入库日期 `2026-07-18`。 |
| `steel_data_workspace.mat` | 暂未直接落库到截图这些业务表 | 当前主要用于分析类接口的数据口径说明，后续如需落库可另建分析结果表。 |

## 4. 后端派生逻辑说明

### 4.1 能源方案派生

对应表：

- `energy_plan`
- `energy_plan_detail`
- `algorithm_task` 中 `task_type = ENERGY_PLAN` 的记录

生成方式：

1. 优先读取 `energy_realtime_data` 中指定日期的能源实时数据。
2. 如果当天有实时数据，则按小时聚合电耗、蒸汽、碳排。
3. 如果当天没有实时数据，则读取 `production_schedule_plan/detail`，用排产电耗预测派生能源明细。
4. 根据峰平谷电价和蒸汽单价计算能源成本。

所以这两张表不是算法组直接给的，而是后端为了能源运行方案接口生成的。

### 4.2 协同优化派生

对应表：

- `joint_optimization_plan`
- `joint_optimization_timeseries`
- `constraint_conflict`
- `algorithm_task` 中 `task_type = JOINT_OPTIMIZATION` 的记录

生成方式：

1. 输入已有排产方案 `production_schedule_plan/detail`。
2. 输入已有能源方案 `energy_plan/detail`。
3. 后端计算降本率、降耗率、执行率、MAPE。
4. 按小时生成协同优化时序明细。
5. 如果能源输出超过阈值，生成约束冲突记录。

所以协同优化目前属于后端基于算法排产和能源数据派生，不是算法组单独输出的最终协同优化文件。

## 5. 当前最需要注意的口径问题

### 5.1 报表统计目前是演示统计

`report_statistic` 当前是为了首页和报表页面联调直接插入的日/月统计数据。它的数值可以服务展示，但不能完全等同于算法组原始输出。

更严谨的后续做法是：

1. 从 `energy_realtime_data`、`energy_plan_detail`、`evaluation_metric` 聚合生成报表统计。
2. 或者明确由算法组提供报表指标文件，再由后端导入。

## 6. 汇报建议

明天可以这样说：

> 目前数据库数据分三类：第一类是算法组真实数据或结果，包括钢铁能源历史数据、1 分钟重采样数据、日级排产 JSON、MPC 调控 CSV；第二类是后端根据算法数据派生出来的能源方案和协同优化结果；第三类是为了系统联调补齐的用户、角色、设备、订单、告警、报表等演示数据。
>
> 其中 `energy_realtime_data`、`steel_energy_dataset`、`mpc_realtime_control`、`production_schedule_plan/detail` 是最接近算法组数据源的表；`energy_plan/detail`、`joint_optimization_plan/timeseries`、`constraint_conflict` 是后端派生表；系统、设备、订单、告警、报表统计目前主要是联调模拟数据。
